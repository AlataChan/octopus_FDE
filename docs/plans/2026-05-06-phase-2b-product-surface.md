# FDE Phase 2B — Product Surface Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Document location:** Project execution plans live in `docs/plans/`. Superpowers is a methodology, not the product-plan directory.

**Naming note:** Product-facing language is FDE / AI 驻场流程工程师. Internal implementation paths may temporarily retain the `loom/` Python namespace until a package rename decision is made.

**Goal:** Make FDE feel like a colleague, not a CLI. Phase 2B turns the Phase 2A service into a usable product surface for three specific people: the **Author** who describes business goals; the **Reviewer** who decides what gets published; and the **Operator/Admin** who manages scopes and credentials. The deliverables: (1) an FDE chat console where the **Persona Brief** (NEW per ADR 0023, rendered first), the workflow brief, the conversation, the IR diff, the **runtime-neutral draft link (Hiagent or Dify, with a target picker)**, and the reviewer summary are all visible in one place; (2) a Web Authoring view that renders an IR as something a non-engineer can read and tweak with natural-language prompts; (3) a semantic-diff viewer that surfaces the changes a reviewer must understand (nodes added/removed/changed, credentials added, policy changes, agent budgets, side effects); (4) a Trace observability surface bound to the runs of the published workflow on its registered runtime; (5) FDE-native RBAC so an Author cannot publish, a Reviewer can, and an Admin manages who is which; (6) accessible Chinese-first UX consistent with the cross-border ecommerce primary and TCM clinic shadow design partners.

**Architecture:** Phase 2A delivered a stateful FastAPI service. Phase 2B keeps that service unchanged and adds:

- **Web app:** Next.js 14 (App Router) + React 18 + TypeScript + Tailwind + shadcn/ui. Server Components where possible; React Server Actions only for non-streaming POSTs. Streaming for chat tokens uses fetch + SSE — not Server Actions.
- **Chat console:** the FDE Session is a first-class object on the server (`loom/sessions/`). A session has: a `PersonaBrief` (per ADR 0023), a `WorkflowBrief`, an `IRDocument` (or none yet), a clarification queue, a chat transcript (`turns`), a `target` (the chosen runtime: `hiagent` | `dify`), a `current_draft` (runtime-neutral handle: `{id, target, target_draft_id, canonical_ast_hash}`), and a current `ReviewSummary`. The web app subscribes to a session and renders all panels in sync — including a `TargetPicker` for switching the active runtime.
- **Semantic diff:** computed server-side from two canonical IRs (per PRD §6.3) and surfaced as a structured object the UI can render — adds, removes, modifies, and side-effect classifications (credentials, policy/budget, external calls, compliance boundary).
- **Trace surface:** consumes the trace tables built in Phase 2A; UI shows per-run, per-node status + duration + payload (subject to ADR 0010 redaction).
- **RBAC:** new ADR (0012) introduces an `actor` model with three roles (Author, Reviewer, Admin) and scope-bounded permissions. The service enforces; the UI hides what the actor is not allowed to act on.

PRD §3 and §6.1 are the canonical references for what the chat console must do. PRD §11 Q8 ("FDE 原生 RBAC 时机") is closed in this phase.

**Tech Stack:** Python 3.11 (existing), FastAPI (existing), SQLAlchemy 2 + Alembic (existing). Web: Next.js 14, React 18, TypeScript 5, Tailwind 3, shadcn/ui (`vercel:shadcn` skill applies if used during execution), TanStack Query, Zustand for local state, Vitest + Playwright. The web app is a separate workspace `apps/web/` so the Python service is unaffected.

- [ ] **Step 1: ADR 0012 — RBAC model**

```markdown
# ADR 0012 — FDE-native RBAC

Status: Proposed → Accepted (after review)
Date: 2026-MM-DD

## Decision

- Three roles: Author, Reviewer, Admin.
- Roles are not hierarchical: an Admin is not automatically a Reviewer.
- An Actor has **one or more roles** (a `set[Role]`) and one or more scopes (e.g. `clinic/kb`, `ecommerce/orders`). The same person who Authors and Reviews holds both roles on a single Actor record.
- Permissions, evaluated as ANY-of (an Actor with `{Reviewer}` qualifies for any "Author OR Reviewer" check):
  - Author: plan, compile, deploy_draft, reverse, view_session within scope.
  - Reviewer: everything Author can do, plus publish (drift-aware), view audit.
  - Admin: manage Actors, manage scopes, sync registry, view audit. **Cannot** plan / publish unless the same Actor *also* holds the Author / Reviewer role.
- Tokens: PASETO v4 (asymmetric); short-lived (15 min) access + 7-day refresh; revocation list in Postgres.
- Service enforces: every route declares required role(s) + scope intersection. `require_role(*roles)` passes if the Actor holds **any** of the listed roles.

## Consequences

- One person can carry multiple roles on the same Actor record. CLAUDE.md §3 spirit ("Author/Reviewer 是角色，不一定是不同人员") is preserved without forcing duplicate Actor rows.
- The web app hides routes/buttons the Actor is not authorized for; the service is the source of truth.
- A Phase 2B audit task verifies four cases: (a) Author-only cannot publish; (b) Reviewer-only can publish; (c) Admin-only cannot publish; (d) Admin+Reviewer can both manage Actors AND publish — same person, one Actor.
```

# loom/auth/actor.py
from __future__ import annotations

from enum import Enum
from typing import Iterable

from pydantic import BaseModel


class Role(str, Enum):
    AUTHOR = "author"
    REVIEWER = "reviewer"
    ADMIN = "admin"


class Actor(BaseModel):
    id: str
    name: str
    email: str
    roles: list[Role]
    scopes: list[str]


def has_any_role(actor: Actor, *roles: Role) -> bool:
    return any(r in actor.roles for r in roles)


def has_scope(actor: Actor, scope: str) -> bool:
    return any(scope == s or scope.startswith(s + "/") for s in actor.scopes)
```

# loom/auth/policy.py
from __future__ import annotations

from dataclasses import dataclass

from loom.auth.actor import Actor, Role, has_any_role, has_scope


@dataclass
class Decision:
    allowed: bool
    reason: str


def can_plan(actor: Actor, scope: str) -> Decision:
    if not has_any_role(actor, Role.AUTHOR, Role.REVIEWER):
        return Decision(False, "needs role author or reviewer")
    if not has_scope(actor, scope):
        return Decision(False, f"actor missing scope {scope}")
    return Decision(True, "ok")


def can_publish(actor: Actor, scope: str) -> Decision:
    if not has_any_role(actor, Role.REVIEWER):
        return Decision(False, "publish requires reviewer role")
    if not has_scope(actor, scope):
        return Decision(False, f"actor missing scope {scope}")
    return Decision(True, "ok")


def can_admin(actor: Actor) -> Decision:
    return Decision(has_any_role(actor, Role.ADMIN), "needs admin role")
```

- [ ] **Step 2: Manager**

`manager.py` exposes:
- `start(actor, scope, intent, persona_id, target="hiagent") → Session` — creates the session in `persona_resolving` state; resolves the Persona Brief from `registry/v1/personas/<persona_id>.yaml` (per ADR 0023); transitions to `clarifying`; runs the workflow-brief generator; populates initial clarification queue.
- `append_turn(session_id, role, text)` — appends to transcript; if Author answered a clarification, mark it answered and re-evaluate brief.
- `materialize_ir(session_id)` — runs Planner with both Persona Brief + Workflow Brief; transitions to `drafted`; pushes draft on the session's `target` runtime via the Phase 2A deployer (RuntimeAdapter); emits audit receipts.
- `apply_edit(session_id, edit_text)` — runs the edit-intent classifier; if recognized, regenerates IR diff; if unrecognized, returns a structured error to the UI.
- `request_review(session_id)` — generates `ReviewSummary` from the current IR + diff against last published IR; transitions to `review_pending`.
- `switch_target(session_id, new_target)` — re-targets the session to a different runtime; recompiles the current IR and pushes a new draft on the new runtime, leaving the original Draft row intact (a workflow can have parallel drafts on multiple runtimes).

Each method emits exactly one audit receipt of the appropriate `op` (Phase 2A `audit.receipts.emit`).

from typing import AsyncIterator

async def stream_planner_tokens(session_id: str) -> AsyncIterator[bytes]:
    """Emits text-delta and structured 'event' frames per SSE protocol."""

    yield b"event: done\ndata: {}\n\n"

- [ ] **Step 2: Side-effect classifier**

```python
# loom/diff/classify.py
from __future__ import annotations

from dataclasses import dataclass
from typing import Literal

from loom.diff.ir_diff import DiffEntry, IRDiff


SideEffect = Literal[
    "credential_added", "credential_removed",
    "external_call_added", "external_call_removed",
    "policy_loosened", "policy_tightened",
    "agent_budget_increased", "agent_budget_decreased",
    "compliance_boundary_changed",
]


@dataclass
class ClassifiedDiff:
    base: IRDiff
    side_effects: list[tuple[DiffEntry, SideEffect]]


def classify(d: IRDiff) -> ClassifiedDiff:
    out: list[tuple[DiffEntry, SideEffect]] = []
    for e in d.entries:
        for se in _detect(e):
            out.append((e, se))
    return ClassifiedDiff(base=d, side_effects=out)


def _detect(e: DiffEntry) -> list[SideEffect]:
    # rules — all structural, no free-text scanning of `rationale`:
    # - new credentials in registry_ref → credential_added
    # - http/code node added → external_call_added
    # - policy budget number went up → policy_loosened (and if agent → agent_budget_increased)
    # - metadata.compliance_class value changed (or any node now references a tool whose
    #   registry entry has tools.<name>.compliance_class != "none" when before it didn't,
    #   per ADR 0021 + IR v0.4) → compliance_boundary_changed
    ...
```

> **Compliance detection is structural, not text-based.** Phase 2A registry entries already carry `pii_class` (per ADR 0010); Phase 3.1's IR v0.4 minor bump adds `metadata.compliance_class` and `tools.<name>.compliance_class`. The diff classifier compares those structured fields between base and head IRs and returns `compliance_boundary_changed` when they differ or when a newly-referenced tool inherits a non-`none` compliance lock. **Do not match on `rationale` substrings** — that approach is rejected by ADR 0021. Until v0.4 lands, this rule degrades to a no-op (rather than firing false positives from rationale heuristics); the rule activates with the Phase 3.1 schema bump.

import zh from "../locales/zh-CN.json" assert { type: "json" };

const zhKeys = new Set(Object.keys(zh as Record<string, unknown>));
