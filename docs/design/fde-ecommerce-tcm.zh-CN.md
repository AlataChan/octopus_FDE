# FDE 中国场景产品设计：跨境电商主线 + 中医诊所辅线

## 1. 定位判断

FDE = **Forward-Deployed Engineer**，中文产品语言是 **AI 驻场流程工程师**。它不是 Front-End Development Engineer，也不是"生成 Dify DSL 的工具"。用户应该感觉自己身边多了一个会追问、会搭流、会改流、会交接的工程师。

中国市场第一切入点采用：

- **主线：跨境电商运营工作流**。多语言客服、订单异常、商品内容本地化、售后升级、经营报表都是高频半结构化流程，业务人员对自动化收益敏感，对治理（凭证/退款/合规审计）也有强需求。
- **辅线：中医诊所运营工作流**。问诊前资料收集、复诊随访、知识库问答、客服分诊、经营日报与电商共享"自然语言请求 → 工作流 → 人审 → 发布"的形状，可作为影子语料验证可迁移性，并把 PII high 类（医疗）案例纳入治理叙事。

当前不把财务/审计、知识产权代理作为主赛道。它们治理价值强，但销售周期、专业责任和合规门槛更重，不适合作为 FDE 第一证明场。

这条路线的核心不是"做电商 SaaS"或"做医疗 AI"，而是先在一个流程密度高、人工审核边界清晰、软件工程资源不足的行业证明：业务人员可以口述流程，FDE 可以把它变成可审查、可回滚、可交接的运行时草稿。

## 2. 为什么先做跨境电商

跨境电商的流程足够真实，又有充分的"必须人审"边界：

- 多语言客服 / 订单异常分诊 / 商品内容本地化 / 售后升级 / 退款审批 / 经营报表（DAU、GMV、退货率）都是高频流程，单个流程触发频率高，价值显性，迭代闭环短。
- 卖家 / 品牌方 / 3PL 通常缺少足够的软件工程师，但有明确的运营、客服主管、退款审核人和老板/财务。
- 业务人员可以口述需求（例：把缺货回复改成多语言模板，把退款超过 500 的转给经理），FDE 可以追问缺失字段、搭出 Dify 草稿，再交给客服主管/退款审核人审核。
- 治理边界清楚：客户 PII（姓名、手机、地址、支付）、退款金额阈值、平台合规（Amazon/Shopify/TikTok Shop 各自规则）、跨境数据流（GDPR/PIPL）都要显性出现在评审摘要里。
- 平台 API（Shopify、Amazon SP-API、TikTok Shop、Shein、Temu、阿里国际、SHEIN 卖家中心、海外仓 WMS）已经成熟稳定，凭证句柄治理可以直接落地。

中医诊所作为辅线的原因是流程形状相近但领域不同：问诊前资料收集、复诊随访、知识库问答、客服分诊、经营日报都能验证 IR、Validator、Compiler 是否过拟合电商语境，同时把 PII high（医疗）案例自然纳入 ADR 0010 的合规叙事。

### 2.1 设计伙伴筛选标准

第一批设计伙伴要能提供真实流程，而不是只提供访谈观点。优先选择同时满足以下条件的卖家、品牌方、电商 SaaS 或 3PL/品牌运营服务商：

- 有 5 个以上高频运营流程，且流程当前依赖人工转述、表格、Slack/飞书、Dify 或其他低代码工具拼接。
- 有明确 Author（运营/客服）、Reviewer（客服主管/退款审核/老板）、Integrator/Admin（技术 OPS / SaaS 集成商）三类责任人；小团队可以一人兼任，但发布权限和审计责任必须能分开。
- 愿意提供脱敏样例、流程口述、现有客服模板/退款规则/库存回写目标，并参与至少一次 Dify 草稿审核。
- 接受 FDE 只交付客服 / 订单 / 售后 / 商品本地化 / 报表草稿，不要求它替代客服坐席发出最终回复（除非有自动发布门控）。
- 有一个可做影子验证的非电商流程（例如内部 HR / 财务表单），或允许用中医诊所样例检验同一 FDE Session 与 IR 是否可迁移。

不适合的第一批伙伴：

- 只想要一个"全自动 ChatGPT 客服坐席"，不接受人审与回退。
- 不愿暴露任何真实订单、客户聊天或退款规则。
- 要求先做全店深度集成（多平台 / 多店铺 / 多仓库一次性接通）后才愿意试用。
- 把 FDE 当成一次性外包交付，而不是可持续创建、修改、审计工作流的能力。

## 3. 角色

- **运营 / 客服主管**：用口述或文本描述流程目标，回答 FDE 的澄清问题。
- **客服主管 / 退款审核 / 老板 / 合规审核人**：审核 Dify 草稿、回复内容边界、退款阈值、升级策略、发布风险。
- **技术交付方 / 电商 SaaS 集成商**：配置 Dify、平台 API、凭证、Webhook、审计与部署。
- **FDE**：需求澄清、工作流简报、IR 生成、校验、编译、推送草稿、自然语言修改、评审摘要与事实源同步。
- **最终用户**：买家、客服、运营人员或（在中医影子场景下）患者；他们不直接操作 IR。

## 4. 核心体验

### 4.1 创建流程

用户说：

> 帮我做一个订单异常分诊流程。每天早上拉一次过去 24 小时所有未发货 + 物流停滞 > 48 小时的订单，按渠道分组，自动给买家发对应语言的安抚消息（不要给出补偿承诺），同时把高价值订单（>$300）单独转给客服主管。

FDE 只能追问阻塞问题：

- 订单数据来自 Shopify、Amazon SP-API、TikTok Shop 还是多个？哪个店铺？
- 高价值阈值用 USD 还是按本币换算？
- 安抚消息的语言是按订单地区自动判断，还是按买家账号语言偏好？
- "客服主管转发"走 Slack / 飞书 / 企微 / 邮件 / Linear？
- 买家回复怎么处理 — 自动归并到这次会话还是新建工单？
- 退款 / 补偿是这个流程的一部分吗，还是另一条流程？

澄清后，FDE 生成工作流简报、IR、校验报告，并推送 Dify 草稿。

FDE 不应该把澄清问题变成咨询访谈。只问阻塞安全生成的问题：触发条件、输入字段、数据源、凭证、输出位置、人审策略、失败重试、超时、买家可见边界。

### 4.2 修改流程

用户说：

> 把高价值阈值从 $300 改成 $500；如果买家 24 小时内没回复，自动发第二条提醒，72 小时还没回复就转给客服主管，并把这单标为待人工跟进。

FDE 必须输出可审查变更摘要：

- 高价值阈值：$300 → $500。
- 新增"未回复 24 小时 → 第二条提醒"分支。
- 新增"未回复 72 小时 → 转客服主管 + 标记待人工跟进"分支。
- 未新增凭证，未扩大数据访问范围。
- 客户 PII 处理范围未变化。

### 4.3 审核与交接

审核人看到的是：

- Dify 可视化草稿。
- 工作流简报。
- 语义 diff。
- 凭证 / 数据源 / 外部调用变化。
- 客户 PII 流向、退款金额阈值、跨境数据流变化（按 ADR 0010 `pii_class` + ADR 0021 `compliance_class`）。
- IR commit、canonical Dify AST hash、反编译状态。

只有 IR、编译 DSL、Dify 草稿和审核摘要一致时，才具备进入审核的条件。

真正的生产发布阻塞、漂移检测、审计链路和 RBAC 属于 Phase 2A/2B，除非执行计划明确提前实现。

### 4.4 可审查交付包

每个工作流样例都必须沉淀成一组可复查产物：

- 原始口述/文本需求。
- FDE 澄清问题、用户回答、仍未解决的假设。
- 工作流简报：触发器、输入、输出、数据源、工具、凭证、审批点、成功标准、合规边界。
- IR、编译 DSL、Dify 草稿链接或导出。
- 自然语言修改样本和对应 IR diff。
- Reviewer 摘要：数据访问、凭证、外部调用、PII 流向、退款 / 补偿金额边界、人审策略、失败处理。
- 识别外 Dify 修改的阻塞记录和修复路径。

## 5. 第一批工作流假设

主线为跨境电商；archetype 02–04 保留为中医影子流程作为跨垂直可迁移性检查：

1. **跨境电商客户 FAQ / KB 问答**（深度场景 1）
   - 输入：商品 KB、政策 KB（退换货、运输时效、保修）、买家提问文本（多语言）、渠道（Amazon / Shopify / TikTok Shop / Shein / Temu）。
   - 输出：带来源的多语言回答、低置信触发升级、渠道差异化语气。
   - 人审：超出 KB 范围或低置信问题进入客服主管复核；保修/退款相关回复必须挂提示语 + 留升级口。

2. **中医问诊前资料收集与分诊** *(影子)*
   - 输入：患者表单、历史记录、主诉文本。
   - 输出：结构化摘要、风险提示、医生 / 客服队列。
   - 人审：所有医疗判断必须进入医生审核。

3. **中医诊所经营 ETL + 摘要** *(影子)*
   - 输入：预约、到诊、复诊、客服、药房/库存数据。
   - 输出：日报 / 周报摘要、异常提醒、待办列表。
   - 人审：负责人确认后发送。

4. **中医复诊与疗程随访** *(影子)*
   - 输入：处方/疗程开始时间、患者反馈、未回复状态。
   - 输出：随访任务、异常升级、记录回写。
   - 人审：异常反馈进入医生复核。

5. **跨境电商订单异常分诊**（深度场景 2）
   - 输入：订单 / 物流 / 退货消息、客服历史、商品资料、多语言模板、平台 API 凭证。
   - 输出：异常分类、多语言回复草稿、退款 / 补发流程（金额阈值触发审批）、售后升级、内容本地化。
   - 人审：超过金额阈值的退款 / 补发必须经客服主管或老板审批；自动回复中不出现"补偿承诺"，只承诺"已升级"。

这 5 类不是演示菜单。Phase 0 必须用真实伙伴 backlog 替换或确认这些假设；如果真实流程明显不同，先重开 IR 范围，不要为了维护文档里的 5 类而硬造样例。

## 6. FDE 能力验收

Phase 1 不能只证明 `intent.json -> IR -> DSL`，必须证明 FDE 这个角色成立：

- 能把口述式需求整理成工作流简报。
- 缺触发器、数据源、凭证、审核策略、输出结构时先问，不猜。
- 能生成 Dify 草稿，而不是只生成本地文件。
- 能接受自然语言修改，并映射成 IR diff。
- 能解释修改对数据、凭证、外部调用、客户 PII / 医疗边界、退款 / 补偿金额边界、人工审核的影响。
- 能阻止识别外 Dify 修改直接发布，并给出回退或扩展 IR 的路径。
- 能让运营 / 客服主管在不懂 IR / Dify DSL 的情况下完成创建和修改。

最低验收证据：

- 至少 2 个深度场景跑通"口述/文本创建 → 澄清 → 工作流简报 → IR → Dify 草稿 → 自然语言修改 → 更新草稿"。
- 深度场景固定为：跨境电商客户 FAQ / KB 问答 + 跨境电商订单异常分诊。
- 每个深度场景至少 15 条创建/编辑语料，语料应主要来自真实流程或真实流程改写。
- Reviewer 能在摘要中看到凭证、数据访问、外部调用、客户 PII、退款 / 补偿阈值、人工审核和失败处理变化。
- 至少 1 个识别外 Dify 修改被硬阻塞，并给出回退、申请 IR 扩展或受控 `code` 节点的修复路径。
- 中医影子流程至少跑通 1 个端到端，证明同一 FDE Session 与 IR 在医疗运营场景仍能用，PII high 处理路径不破。

## 7. 设计原则

- **角色优先**：用户买的是 AI 驻场流程工程师，不是编译器。
- **人审是产品的一部分**：电商场景退款 / 补偿 / 跨境合规、中医场景诊断 / 处方 / 患者可见发布都必须经过人审；审核不是阻力，而是可信交付链路。
- **少问但必须问**：FDE 只追问阻塞信息，但不能为了省一轮对话而编造默认值（特别是金额阈值、退款规则、医疗边界）。
- **运行时是审核面**：Dify 是可视化审核和交接界面；Git/IR 是事实源。
- **合规边界显性化**：客户 PII、医疗暗示、退款金额、凭证变化必须出现在评审摘要里（结构化字段，不是 rationale 自由文本）。
- **辅线验证迁移性**：中医诊所不是第二个产品，而是防止 IR 过度贴合跨境电商的验证集。
- **先深后宽**：Phase 1 宁可把 2 个流程做深，也不要把 5 个流程都做成无法评审的浅层 demo。

## 8. Phase 1 必须补齐的设计产物

- 5 个真实跨境电商流程的口述请求样本（其中 2 个为深度场景：客户 FAQ + 订单异常分诊）。
- 每个流程的预期澄清问题。
- 每个流程的自然语言修改样本。
- 每个流程的 Reviewer 关注点和发布阻塞条件。
- 1 个中医诊所影子流程，用来验证同一 FDE Session 和 IR 能否迁移到医疗运营垂直。
- FDE 会话日志、工作流简报、IR、Dify 草稿、评审摘要之间的端到端样例。

## 9. 关键风险与护栏

- **客户 PII 外溢**：买家姓名、手机、地址、支付信息属于 medium / high `pii_class`，必须按 ADR 0010 在 trace ingest 强制处理；任何把 PII 直接写到 LLM prompt 或日志的路径都必须被拦截。
- **退款 / 补偿越权**：自动回复中不允许出现具体金额承诺；退款 / 补发金额触达阈值时必须落到人审队列，自动发布路径必须被 IR Validator 拦截。
- **中医医疗边界外溢**：在中医影子场景下，任何诊断、处方、疗效承诺、患者端自动发布都必须被拦截，并转为"医生/负责人审核任务"。
- **跨境数据合规**：欧洲买家 PII、平台禁运商品、版权 / 商标内容必须在 Reviewer 摘要中显性出现；GDPR / PIPL 相关流程触发时增加合规审核 step。
- **数据和凭证扩权**：新增数据源、买家信息字段、外部 API、Webhook 或凭证句柄时，Reviewer 摘要必须显式高亮（结构化 `compliance_class` + `pii_class`，不是 rationale 自由文本）。
- **影子垂直失控**：中医诊所只服务于迁移性验证；不能在主线未验证前拆出独立销售路线、独立产品叙事或独立 roadmap。
- **过度集成拖慢验证**：Phase 1 优先使用脱敏样例、导入导出、模拟凭证和人工回写；深集成放到设计伙伴确认价值之后。
- **演示流伪成功**：如果样例不是来自真实流程，必须标记为 synthetic，不能混入 Phase 1 成功率口径。
- **只会生成不会修改**：不能接受"创建能跑、编辑靠人工改 Dify"。自然语言编辑与事实源同步是 FDE 角色成立的必要条件。

## 10. 明确非目标

- 不替代客服坐席发出最终回复（除非伙伴明确同意自动发布门控 + 限定金额阈值）。
- 不在 Phase 1 做面向买家的全自动退款 / 补偿决策。
- 不提供医疗诊断（在中医影子场景下）。
- 不提供处方建议（同上）。
- 不承诺疗效（同上）。
- 不绕过医生 / 负责人 / 合规人员审核（同上）。
- 不把中医诊所做成并行主产品。
